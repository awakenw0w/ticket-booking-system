# Пояснительная записка

Тема: разработка информационной системы бронирования и продажи билетов на мероприятия с различными видами билетов.

Автор: Быстров Егор, группа 3-1ИС.

Стек: Laravel, PHP, SQLite, HTML, CSS, JavaScript, GitHub.

## Введение

Заказчику требуется система, которая помогает вести мероприятия, категории билетов и бронирования в одном месте. Без автоматизации менеджер вынужден вручную проверять остатки билетов, вести списки клиентов и отдельно считать выручку. Это повышает риск ошибок: можно продать больше билетов, чем доступно, потерять отмену бронирования или неверно посчитать отчет.

Цель работы: реализовать MVP информационной системы для бронирования и продажи билетов на мероприятия.

Задачи:

- проанализировать предметную область;
- выделить роли пользователей и функциональные требования;
- спроектировать структуру данных;
- реализовать основу backend на Laravel;
- подготовить тестовые данные;
- описать будущий API;
- добавить автотесты для проверки структуры БД;
- вести код в GitHub через ветки и коммиты.

## Анализ предметной области

В системе участвуют администратор, менеджер и клиент. Администратор отвечает за общую настройку и пользователей. Менеджер создает мероприятия, задает категории билетов, контролирует бронирования и отчеты. Клиент выбирает мероприятие, бронирует билеты и при необходимости отменяет бронирование.

MVP включает:

- управление мероприятиями;
- учет одной или нескольких категорий билетов;
- создание бронирования;
- отмену бронирования;
- фиксацию оплаты;
- отчеты по бронированиям, выручке и заполненности.

Функциональные требования вынесены в `docs/requirements.md`.

## Архитектура

Проект строится как трехзвенная информационная система:

- клиентская часть отображает интерфейс и отправляет запросы;
- API принимает запросы, валидирует данные и выполняет бизнес-логику;
- база данных хранит пользователей, роли, мероприятия, категории билетов и бронирования.

На первом этапе реализована серверная основа: миграции, модели, связи и сидер. На втором этапе добавлены API-контроллеры для CRUD-операций с мероприятиями, категориями билетов и бронированиями. На третьем этапе реализован клиентский интерфейс MVP, который обращается к API и позволяет выполнять основные пользовательские действия. На четвертом этапе добавлены отчеты по бронированиям, выручке и заполненности мероприятий.

## Жизненный цикл разработки

Работа выполнялась по спиралевидной модели жизненного цикла: каждый виток включал уточнение требований, проектирование, реализацию, проверку и фиксацию результата в Git. Такой подход выбран потому, что курсовой проект постепенно развивается от требований и модели данных к API, интерфейсу, отчетам и документации.

Этапы жизненного цикла:

- анализ предметной области и выделение MVP;
- проектирование модели данных и API;
- реализация серверной части;
- реализация клиентского интерфейса;
- тестирование backend, API и GUI;
- оформление эксплуатационной документации;
- подготовка материалов для защиты.

Каждый этап оформлялся отдельной веткой Git. Это позволяет показать последовательность разработки, отделить изменения по смыслу и упростить проверку результата.

## Модель данных

Основные сущности:

- `roles` - роли пользователей;
- `users` - пользователи системы;
- `events` - мероприятия;
- `ticket_categories` - категории билетов внутри мероприятия;
- `bookings` - бронирования клиентов.

Связи:

- роль имеет много пользователей;
- пользователь имеет много бронирований;
- мероприятие имеет много категорий билетов;
- категория билетов имеет много бронирований.

Подробная таблица данных описана в `docs/data-model.md`.

## Реализация

Серверная часть реализована на Laravel. Для хранения данных используется SQLite, что удобно для учебного проекта и локальной демонстрации. Структура базы создается миграциями, а тестовые данные загружаются сидером.

Основные элементы реализации:

- модели `Event`, `TicketCategory`, `Booking`, `Role`, `User`;
- связи Eloquent между мероприятиями, категориями билетов, бронированиями и пользователями;
- API-контроллеры для мероприятий, категорий билетов, бронирований и отчетов;
- проверка доступного остатка билетов перед созданием бронирования;
- отдельные операции отмены и оплаты бронирования;
- frontend без сборщика, чтобы проект можно было быстро открыть локально.

Клиентская часть реализована как рабочий интерфейс менеджера. Пользователь выбирает мероприятие, просматривает остатки билетов, оформляет бронирование и контролирует его статус.

## Проект API

API проектируется вокруг основных сущностей MVP:

- `/api/events` - мероприятия;
- `/api/events/{event}/ticket-categories` - категории билетов мероприятия;
- `/api/bookings` - бронирования;
- `/api/reports/*` - отчеты.

Документация API находится в `docs/api.md`. Реализованные endpoint'ы поддерживают создание, чтение, изменение и удаление мероприятий, категорий билетов и бронирований. Для бронирования добавлены отдельные операции отмены и оплаты.

## Клиентская часть

Frontend реализован как HTML, CSS и JavaScript без сборщика. Интерфейс работает с API backend по адресу `http://127.0.0.1:8000/api`.

Основные экраны и блоки:

- список мероприятий;
- карточка выбранного мероприятия;
- таблица категорий билетов;
- форма добавления категории;
- форма создания бронирования;
- журнал бронирований;
- действия оплаты и отмены активного бронирования.
- блок отчетов с фильтрами, сводными карточками и таблицами.

Интерфейс рассчитан на рабочий сценарий менеджера: сначала выбирается мероприятие, затем проверяются категории и остатки билетов, после этого создается бронирование клиента.

## Отчеты

В системе реализованы три отчета:

- отчет по бронированиям показывает количество броней, билетов и сумму в разрезе статусов;
- отчет по выручке учитывает только оплаченные бронирования и группирует результат по мероприятиям;
- отчет по заполненности показывает общее количество билетов, активные билеты, доступный остаток и процент заполненности.

Отчеты доступны через API и отображаются в клиентском интерфейсе.

На этапе 2 добавлены API-тесты:

- создание бронирования;
- проверка ограничения по доступному остатку билетов;
- отмена бронирования;
- отметка бронирования как оплаченного;
- запрет удаления оплаченного бронирования.

На этапе 3 проведена ручная проверка GUI в браузере:

## Глоссарий

- API - интерфейс взаимодействия клиентской и серверной части.
- CRUD - создание, чтение, изменение и удаление данных.
- MVP - минимально жизнеспособный продукт.
- Бронирование - временное закрепление билетов за клиентом.
- Категория билета - тип билета внутри мероприятия, например стандарт или VIP.
- Миграция - файл изменения структуры базы данных.
- Сидер - файл заполнения базы тестовыми данными.
