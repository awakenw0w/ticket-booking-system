# Требования к информационной системе

Тема: бронирование и продажа билетов на мероприятия с различными видами билетов.

Цель системы: автоматизировать создание мероприятий, учет категорий билетов, бронирование мест клиентами, отмену бронирований и подготовку простых отчетов по продажам и загрузке мероприятий.

## Роли пользователей

- Администратор управляет справочниками, пользователями, мероприятиями и отчетами.
- Менеджер создает мероприятия, настраивает категории билетов и обрабатывает бронирования.
- Клиент просматривает мероприятия, бронирует билеты и отменяет свои бронирования.

## MVP

В минимальную рабочую версию входят:

- список мероприятий;
- создание и изменение мероприятий;
- категории билетов для каждого мероприятия;
- оформление бронирования по категории билета;
- отмена бронирования;
- просмотр статуса бронирования;
- базовые отчеты по мероприятиям, бронированиям и выручке.

## Функциональные требования

1. Система должна отображать список доступных мероприятий.
2. Система должна показывать карточку мероприятия с названием, описанием, местом, датой и статусом.
3. Система должна позволять администратору или менеджеру создавать мероприятие.
4. Система должна позволять администратору или менеджеру редактировать данные мероприятия.
5. Система должна позволять менять статус мероприятия: черновик, опубликовано, завершено, отменено.
6. Система должна хранить несколько категорий билетов для одного мероприятия.
7. Система должна поддерживать мероприятие с одной категорией билетов.
8. Система должна поддерживать мероприятие с несколькими категориями билетов.
9. Система должна хранить цену каждой категории билетов.
10. Система должна хранить общее количество билетов в каждой категории.
11. Система должна рассчитывать доступный остаток билетов с учетом активных бронирований и оплаченных билетов.
12. Система должна позволять клиенту создать бронирование на выбранное мероприятие и категорию билета.
13. Система должна проверять, что количество запрошенных билетов не превышает доступный остаток.
14. Система должна сохранять данные клиента при бронировании: имя, почту и телефон.
15. Система должна присваивать бронированию статус `reserved`.
16. Система должна рассчитывать итоговую сумму бронирования по цене категории и количеству билетов.
17. Система должна позволять отменить активное бронирование.
18. Система должна присваивать отмененному бронированию статус `cancelled`.
19. Система должна сохранять дату и время отмены бронирования.
20. Система должна позволять отметить бронирование как оплаченное.
21. Система должна присваивать оплаченному бронированию статус `paid`.
22. Система должна сохранять дату и время оплаты.
23. Система должна показывать список бронирований по мероприятию.
24. Система должна показывать список бронирований конкретного клиента.
25. Система должна формировать отчет по количеству бронирований за период.
26. Система должна формировать отчет по выручке за период.
27. Система должна формировать отчет по заполненности мероприятий.
28. Система должна предоставлять API для обмена данными между клиентской частью и сервером.
29. Система должна возвращать понятные ошибки API при неверных данных запроса.
30. Система должна хранить роли пользователей для разделения прав доступа.

## Нефункциональные требования

- Серверная часть реализуется на Laravel.
- Данные хранятся в реляционной базе данных через миграции Laravel.
- Клиентская часть обращается к серверной через API.
- Проект хранится в GitHub и ведется через ветки.
- Для проверки используются автотесты Laravel и ручной чек-лист.
