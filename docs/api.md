# Проект API

Документ фиксирует API для следующих этапов разработки. На этапе 1 реализована модель данных, а контроллеры API будут добавляться после согласования структуры.

Базовый префикс будущих запросов: `/api`.

## Мероприятия

### `GET /api/events`

Назначение: получить список мероприятий.

Ответ:

```json
[
  {
    "id": 1,
    "title": "Летний музыкальный фестиваль",
    "location": "Городской парк",
    "starts_at": "2026-06-07T19:00:00",
    "status": "published"
  }
]
```

### `POST /api/events`

Назначение: создать мероприятие.

Поля запроса:

- `title`
- `description`
- `location`
- `starts_at`
- `status`

### `PUT /api/events/{event}`

Назначение: изменить мероприятие.

### `DELETE /api/events/{event}`

Назначение: удалить мероприятие или перевести его в неактивное состояние. Итоговое поведение будет уточнено на этапе CRUD.

## Категории билетов

### `GET /api/events/{event}/ticket-categories`

Назначение: получить категории билетов выбранного мероприятия.

### `POST /api/events/{event}/ticket-categories`

Назначение: создать категорию билетов.

Поля запроса:

- `name`
- `price`
- `quantity`

### `PUT /api/ticket-categories/{ticketCategory}`

Назначение: изменить цену, название или количество билетов.

### `DELETE /api/ticket-categories/{ticketCategory}`

Назначение: удалить категорию, если по ней нет активных бронирований.

## Бронирования

### `GET /api/bookings`

Назначение: получить список бронирований с фильтрами по мероприятию, клиенту и статусу.

### `POST /api/bookings`

Назначение: создать бронирование.

Поля запроса:

- `ticket_category_id`
- `customer_name`
- `customer_email`
- `customer_phone`
- `quantity`

Ожидаемая логика:

- проверить существование категории билета;
- проверить доступный остаток;
- рассчитать `total_price`;
- сохранить бронирование со статусом `reserved`.

### `PATCH /api/bookings/{booking}/cancel`

Назначение: отменить бронирование.

Ожидаемая логика:

- разрешить отмену только для бронирования со статусом `reserved`;
- изменить статус на `cancelled`;
- заполнить `cancelled_at`.

### `PATCH /api/bookings/{booking}/pay`

Назначение: отметить бронирование как оплаченное.

Ожидаемая логика:

- разрешить оплату только для бронирования со статусом `reserved`;
- изменить статус на `paid`;
- заполнить `paid_at`.

## Отчеты

### `GET /api/reports/bookings`

Назначение: отчет по количеству бронирований за период.

Параметры:

- `date_from`
- `date_to`
- `status`

### `GET /api/reports/revenue`

Назначение: отчет по выручке за период.

Параметры:

- `date_from`
- `date_to`
- `event_id`

### `GET /api/reports/events-occupancy`

Назначение: отчет по заполненности мероприятий.

## Ошибки

Планируемый формат ошибки:

```json
{
  "message": "Недостаточно доступных билетов",
  "errors": {
    "quantity": ["Доступно только 3 билета"]
  }
}
```

Для ошибок валидации используется статус `422`, для отсутствующих записей - `404`, для запрещенных операций - `403`.
