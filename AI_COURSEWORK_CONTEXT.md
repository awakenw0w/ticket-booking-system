# Контекст проекта для нейросети, которая будет писать курсовую

Этот файл нужен не как готовая пояснительная записка, а как подробный технический контекст для другой нейросети. По нему можно составить текст курсовой работы, описание этапов разработки, архитектуры, базы данных, интерфейса, тестирования и ограничений проекта.

## Тема проекта

Информационная система бронирования и продажи билетов на мероприятия с различными видами билетов.

Система должна позволять:

- создавать мероприятия;
- заводить одну или несколько категорий билетов для каждого мероприятия;
- бронировать билеты клиентом;
- отменять бронирование;
- отмечать бронирование как оплаченное;
- смотреть отчеты и аналитику по бронированиям, выручке и заполненности мероприятий.

## Стек

- Backend: PHP 8.3+, Laravel 13.
- База данных: SQLite.
- Frontend: HTML, CSS, JavaScript без тяжелого фреймворка.
- Тестирование: PHPUnit / Laravel Feature Tests.
- Деплой frontend: Vercel как статический сайт.
- GitHub: ветки по этапам и коммиты на русском языке.

## Основные сущности базы данных

### roles

Таблица ролей для основы многопользовательской информационной системы.

Примеры ролей:

- admin;
- manager;
- client.

### users

Пользователи системы. Связаны с ролями через `role_id`. В текущем интерфейсе полноценная авторизация не реализована, но модель данных подготовлена для дальнейшего расширения.

### events

Мероприятия.

Основные поля:

- `title` - название мероприятия;
- `description` - описание;
- `location` - место проведения;
- `starts_at` - дата и время начала;
- `status` - статус: `draft`, `published`, `finished`, `cancelled`.

### ticket_categories

Категории билетов для мероприятия.

Основные поля:

- `event_id` - связь с мероприятием;
- `name` - название категории, например "Стандарт", "VIP";
- `price` - цена билета;
- `quantity` - общее количество билетов в категории.

### bookings

Бронирования.

Основные поля:

- `user_id` - необязательная связь с пользователем;
- `ticket_category_id` - категория билетов;
- `customer_name`;
- `customer_email`;
- `customer_phone`;
- `quantity` - количество билетов;
- `status` - `reserved`, `cancelled`, `paid`;
- `total_price` - итоговая сумма;
- `reserved_at`, `cancelled_at`, `paid_at` - даты операций.

## Backend API

API реализован в Laravel. Основные маршруты находятся в `backend/routes/api.php`.

### Мероприятия

- `GET /api/events` - список мероприятий.
- `POST /api/events` - создание мероприятия.
- `GET /api/events/{event}` - просмотр мероприятия.
- `PATCH /api/events/{event}` - обновление мероприятия.
- `DELETE /api/events/{event}` - удаление мероприятия.

### Категории билетов

- `GET /api/events/{event}/ticket-categories` - категории выбранного мероприятия.
- `POST /api/events/{event}/ticket-categories` - добавление категории.
- `GET /api/ticket-categories/{ticketCategory}` - просмотр категории.
- `PATCH /api/ticket-categories/{ticketCategory}` - обновление категории.
- `DELETE /api/ticket-categories/{ticketCategory}` - удаление категории.

### Бронирования

- `GET /api/bookings` - список бронирований.
- `POST /api/bookings` - создание бронирования.
- `GET /api/bookings/{booking}` - просмотр бронирования.
- `PATCH /api/bookings/{booking}` - изменение активной брони.
- `DELETE /api/bookings/{booking}` - удаление неоплаченной брони.
- `PATCH /api/bookings/{booking}/cancel` - отмена активной брони.
- `PATCH /api/bookings/{booking}/pay` - отметка брони как оплаченной.

### Отчеты

- `GET /api/reports/bookings` - сводка по бронированиям и группировка по статусам.
- `GET /api/reports/revenue` - выручка по оплаченным броням.
- `GET /api/reports/events-occupancy` - заполненность мероприятий.

## Frontend после упрощения

Интерфейс сделан не как лендинг, а как несколько простых страниц внутри одного статического приложения.

### Страница "Мероприятия"

Для клиента:

- список мероприятий;
- карточка выбранного мероприятия;
- таблица категорий билетов;
- форма бронирования.

### Страница "Личный кабинет"

Упрощенный кабинет без авторизации:

- пользователь вводит email;
- система показывает бронирования, связанные с этой почтой;
- для активных броней доступны действия оплаты и отмены.

### Страница "Админка"

Для администратора:

- создание нового мероприятия;
- добавление категорий билетов к мероприятию;
- просмотр всех бронирований;
- краткая аналитика.

### Страница "Отчеты"

Для администратора:

- фильтр по датам, статусу и мероприятию;
- сводные карточки;
- таблица бронирований по статусам;
- таблица выручки по мероприятиям;
- таблица заполненности мероприятий.

## Валидация и ошибки

Проверка данных сделана на двух уровнях.

### Frontend

Frontend проверяет данные до отправки на сервер:

- обязательность названия и места мероприятия;
- дату в формате `ГГГГ-ММ-ДД`;
- время в формате `ЧЧ:ММ`;
- корректность email;
- положительное целое количество билетов;
- цену от 0;
- корректный период отчетов.

Ошибки показываются пользователю рядом с формой и дополнительно через всплывающее уведомление.

### Backend

Laravel проверяет данные повторно на сервере:

- `required`, `string`, `max`, `email`, `date`, `integer`, `numeric`, `min`;
- существование связанных записей через `exists`;
- допустимые статусы через `in`;
- запрет некорректного фильтра статуса в отчете выручки;
- проверка доступного количества билетов перед созданием или изменением бронирования.

Для основных ошибок добавлены русские сообщения. Это важно раскрыть в курсовой: клиентская проверка нужна для удобства пользователя, серверная проверка нужна для надежности и защиты данных.

## Этапы разработки

### Этап 1. Доменная модель и база данных

Были описаны основные сущности предметной области: мероприятия, категории билетов, бронирования, пользователи и роли. Добавлены миграции, Eloquent-модели, связи между моделями и seed-данные.

Главная цель этапа: подготовить фундамент системы и доказать, что структура БД соответствует предметной области.

### Этап 2. Backend API

Были добавлены контроллеры и маршруты API для CRUD-операций:

- мероприятия;
- категории билетов;
- бронирования;
- отмена бронирования;
- отметка оплаты.

Также добавлена бизнес-логика проверки количества доступных билетов.

### Этап 3. Первый frontend MVP

Был создан первый клиентский интерфейс, который подключался к API и позволял:

- выбрать мероприятие;
- посмотреть категории билетов;
- создать бронирование;
- отменить или оплатить бронь.

### Этап 4. Отчеты

Были добавлены backend-отчеты и отображение отчетов на frontend:

- количество бронирований;
- количество билетов;
- сумма броней;
- выручка только по оплаченным броням;
- заполненность мероприятий.

### Этап 5. Документационный пакет

Подготавливались материалы для защиты: пояснительная записка, руководство пользователя, инструкция по развертыванию, чек-лист тестирования и структура презентации. Позже эти материалы были перенесены пользователем отдельно, поэтому из GitHub были удалены подробные markdown-документы.

### Этап 6. Очистка GitHub и краткий README

Из репозитория удалили подробные markdown-документы и документационные ветки. В GitHub оставили кодовые ветки и короткий `README.md` с базовым запуском проекта.

### Этап 7. Упрощение интерфейса, кабинет, админка, валидация и Vercel

Frontend переделан в более простой вид:

- несколько страниц вместо одного перегруженного экрана;

- личный кабинет по email;
- админка для мероприятий, категорий, бронирований и аналитики;

- русские сообщения серверной валидации;
- тесты backend-валидации;
- подготовка статического деплоя frontend на Vercel.

## Что важно раскрыть в тексте курсовой

1. Предметная область: бронирование и продажа билетов на мероприятия.
2. Почему нужны категории билетов: разные цены и лимиты мест.
3. Почему бронирование имеет статусы: активная бронь, отмена, оплата.
4. Почему нужна проверка доступности билетов на сервере.
5. Почему отчеты важны для администратора.
6. Почему интерфейс разделен на клиентскую часть, личный кабинет, админку и отчеты.
7. Чем отличается frontend-валидация от backend-валидации.
8. Какие ограничения есть в текущей версии: нет полноценной авторизации, кабинет работает по email, backend запускается локально.
9. Как проект можно развивать дальше: авторизация, роли в интерфейсе, экспорт отчетов, полноценный деплой backend.

## Ограничения текущего проекта

- Авторизация не реализована как полноценный login/password flow.
- Личный кабинет ищет бронирования по email.
- Админка не закрыта паролем, потому что проект ориентирован на учебный MVP.
- Vercel подходит для статического frontend. Laravel backend для демонстрации запускается локально по адресу `http://127.0.0.1:8000/api`.
- Для полного production-деплоя нужно отдельно размещать Laravel backend и базу данных на сервере.

## Команды для проверки

Backend:

```powershell
cd backend
composer install
Copy-Item .env.example .env -Force
php artisan key:generate
New-Item .\database\database.sqlite -ItemType File -Force | Out-Null
php artisan migrate:fresh --seed
php artisan test
php artisan serve --host=127.0.0.1 --port=8000
```

Frontend локально:

```powershell
cd frontend
python -m http.server 5173 --bind 127.0.0.1
```

Frontend build для Vercel:

```powershell
npm install
npm run build
```
